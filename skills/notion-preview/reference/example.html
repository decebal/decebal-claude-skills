What the limiter counts

The limiter is a token bucket per API key. Each request spends one token; the bucket refills at a fixed rate up to a burst ceiling. A request that finds the bucket empty is rejected with 429 Too Many Requests and a Retry-After header.

🔑

Keyed requests only. Unauthenticated requests are limited per source address at the edge, before they reach this limiter, and are not covered here.

Where one key holds many concurrent connections, the bucket drains faster than any single connection suggests. That is the state this page names key-saturated.

Requests are counted at the gateway rather than per service instance, because the load balancer spreads one client across every instance. A per-instance count lets a client exceed the limit by a factor of the instance count; only a shared count holds the bound. Added after the load test showed per-instance counting admitting 3.8× the configured rate.

Architecture

How the parts fit together.

The check runs once per request, before routing, against the shared counter store. The key-saturated branch sits last in admitRequest, so every narrower rejection — a revoked key, a suspended account — is offered the request first.

# Background

## What the limiter counts

The limiter is a token bucket per API key. Each request spends one token; the bucket refills at a fixed rate up to a burst ceiling. A request that finds the bucket empty is rejected with `429 Too Many Requests` and a `Retry-After` header.

Where one key holds many concurrent connections, the bucket drains faster than any single connection suggests. That is the state this page names `key-saturated`.

Requests are counted at the gateway rather than per service instance, because the load balancer spreads one client across every instance. A per-instance count lets a client exceed the limit by a factor of the instance count; only a shared count holds the bound.

# Architecture

The check runs once per request, before routing, against the shared counter store. The `key-saturated` branch sits last in `admitRequest`, so every narrower rejection — a revoked key, a suspended account — is offered the request first.

## Variables

Each row is a bound read once per request. Direction says who supplies the value; a bound with no configuration source is compiled in.

| Full Name | Variable | Value | Direction | Status |
| --- | --- | --- | --- | --- |
| Refill Rate Per Second | `refillRatePerSecond` | 25 | Config → Gateway | Active |
| Burst Ceiling | `burstCeiling` | 100 | Config → Gateway | Active |
| Counter Sync Interval | `counterSyncIntervalMs` | 50 | Config → Gateway | Proposed |
| Retry After Floor | `retryAfterFloorSeconds` | 1 | Config → Gateway | Active |

`refillRatePerSecond` is the bound that decides the branch. Raising it from 20 to 25 cut rejections for the busiest integration partners to 1%, with p99 latency unchanged.

# Behaviour by version and product

| Version | Behaviour |
| --- | --- |
| API 2.x and earlier | No per-key limit. An overloaded service returns a generic `503` and no retry advice. |
| API 3.0.0 | Per-key limit with `Retry-After`. `burstCeiling` is 100. |

# Open decisions

- Request cost is not weighted, so one batch call spends the same single token as a health check, and is under-limited — a client can submit a thousand-item batch for one token. Settled by charging a batch per item rather than by any further measurement work.
- `retryAfterFloorSeconds` at 1 is knowingly unfitted against the new refill rate. It spaces retries correctly for every client library tested, which is the only condition it is trusted in.
